# 判断维度：按任务类型取

工厂不会只写代码（#9157）：SEO、文章、书、视频、数据分析、情报收集都会成为工厂任务。
portfolio 的判断维度因此**不写死成代码**：每个 epic 计划先定 `taskType`，下面每个维度的写法按类型取。
同一个计划里成员可以混类型（比如 code + content），每个成员各按自己的类型写验收。

## 六个维度

| 维度 | 必须回答的问题 | 写不出来时 |
|---|---|---|
| 价值与为什么现在 | 做完以后哪件事变得可能，或哪个风险消失；为什么不是下个季度 | 判 `trivial` 或 `defer` |
| 鸡毛蒜皮 | 收益是否抵得上一个 run 的代价加一次 review；是不是一次性观察 | 判 `trivial`，写 `wakeOn` |
| 爆破范围 | 见下表，按类型 | 判 `investigate` |
| 代价 | 大约多少个 run（一个 run ≈ 一个 PR 或一份交付物）；需要哪些特殊环境 | 判 `investigate` |
| 依赖与顺序 | 先要什么落地；它挡住了谁 | 画不出依赖 = 还没读懂，不排 |
| 版本归属 | beta（main 上的提交）还是 stable（`[release]`）；归哪个里程碑 | 默认 beta；要进 stable 的判 `human` |

## 爆破范围、代价、验收：按类型

任务类型只是 work object 上的字段，不对应某一种 agent：任何 agent 都能接任何类型的 work，
派工只按资源（名额、CPU、内存、磁盘、GPU、装了哪些工具和环境）。所以「代价」一列写的是这类 work
**要声明的资源**，计划里再写一句「现在有没有哪台机器能提供」。

| 类型 | 爆破范围 | 代价的单位与要声明的资源 | 验收 |
|---|---|---|---|
| `code` | 哪些包；是否 breaking（公共 API、CLI 参数、存储格式、协议）；迁移成本（数据迁移、调用方改动、文档） | run 数；部署 staging、真机设备、多机等（名称取仓库自己的环境） | 每个成员一个 **mutation pair**：改回去哪条测试变红、改上哪条变绿；epic 级一个 **accept test**，在真实入口（`arc` CLI、活环境）上跑 |
| `content` | 品牌和声誉、对外承诺、版权和引用 | 篇数和字数；需要谁的声音（`factory_portfolio_direction_sources` 里的写作风格） | **rubric**（结构、论点、风格符合写作风格文档、原创性）+ **事实核查清单**：每条事实陈述对一个来源或一段代码 |
| `seo` | 站点流量、索引状态、对外可见的页面 | 页面数；站点部署权限 | **可测指标**（索引页数、目标词排名、CWV、结构化数据通过率），写明基线、目标和**复测时间**（发布后 N 天的延迟验收） |
| `media` | 品牌、版权、素材授权 | 时长；工具（ffmpeg、GPU） | 技术规格（分辨率、码率、时长、字幕）+ 节奏 rubric |
| `data` | 结论被谁引用、哪个决定依赖它 | 数据量；数据源访问权限 | **可复算**：输入快照的位置、脚本、同输入同输出；关键数字附正控（数到 0 要证明不是没数） |
| `intel` | 方向判断被它左右 | 搜索次数和阅读量；联网 | 每条结论附**引用链接**；关键结论至少两个独立来源；明确写出哪些说法来源单一、未经核实 |
| `process` | 流程立法（AGENTS.md、`.claude/`、`docs/architecture/`） | — | 工厂不能做：判 `excluded`，交给人 |

**对外发布一律按 R2**：文章上线、SEO 改动上线、视频发布、对外消息、npm/release，不管任务类型。
内部草稿、分支上的交付物都是 R0。

## 市场分析和情报收集本身是一种任务（`intel`）

方向类主题（要不要做、跟谁竞争、生态往哪走）在排序前要有事实。portfolio 可以自己做一轮轻量调研，
也可以判 `investigate`，把调研派成一个 `intel` 任务。

一次 `intel` work 要声明的资源（任何 agent 都能接，派工只看哪台机器提供得了这些资源）：
- 工具：联网搜索和抓取（出站网络）；
- 输入：本仓库的只读检出，用来判断「我们已经有什么」；`factory_portfolio_direction_sources` 里的方向框架；
- 不需要 GPU、特殊设备或凭据；磁盘和内存按一次普通 run 计。

rubric：能区分一手来源（官方博客、规范、changelog）和二手转述；结论对得上代码现状。

验收：
- 每条结论有引用；单一来源的标出来；
- 结论落到一个可执行的判断上（做 / 不做 / 等什么信号），并写成 `wakeOn`；
- 抽一条关键结论，换一个引擎独立复查来源，结论一致才算通过。

#9154 的 dry-run 是第一份样本：它对每个排进前列的方向查了竞品和生态，结论附链接，
并把「什么信号出现时重新考虑」写进被砍条目的 `wakeOn`。

## 用所有者的工程观检查

排序前对每个主题问三句：
1. 这个抽象 10 年后还成立吗？（还是在让马车更快）
2. 它失败时长什么样？读完计划不知道它怎么失败，计划就是假的。
3. 这是不是在错误方向上勤奋：做了很多，但世界没有变简单。
